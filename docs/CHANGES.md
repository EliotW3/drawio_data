# drawio_data — Fork Change Log

This file records every change made to this fork of draw.io and its effect on the application and codebase. It is the companion to [ARCHITECTURE.md](ARCHITECTURE.md): the architecture guide describes how the code works *now*, and this log explains *what was changed from upstream and why*.

The upstream release log is [ChangeLog](../ChangeLog) in the repository root. Do not add fork changes there.

## How to record a change

- Add a new entry at the **top** of [Change entries](#change-entries) with the next ID (`CHG-006`, `CHG-007`, …), and add a row to the [Change index](#change-index).
- Fill in every heading of the template below. Write "None" rather than deleting a heading.
- Reference [ARCHITECTURE.md](ARCHITECTURE.md) sections by number (e.g. "§12.2") and update those sections in the same change, so that the architecture guide always describes the current code.
- List anything left unfinished under **Follow-ups**, and keep [Open follow-ups](#open-follow-ups) in sync until the item is resolved.

```markdown
### CHG-NNN — <short title>

- **Date:** YYYY-MM-DD
- **Status:** Done | Done, follow-ups pending | Reverted
- **ARCHITECTURE.md sections affected:** §x.y, …

**Motivation** — why the change was made.

**What changed for users** — visible behaviour before → after.

**What changed in the code** — files, functions, removed/added APIs.

**Impact on the codebase** — dependencies, load order, bundles, server, configuration, compatibility (desktop, embed, viewer).

**Verification** — how it was tested and the result.

**Follow-ups** — remaining work, or "None".
```

### CHG-005 — Data flow diagrams, phase 3: actions

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §20

**Motivation**

Phase 3 of [DATAFLOW.md](DATAFLOW.md): the four actions (Export, Filter, Validation, Addition), the connection rules, and the streams that carry datasets from one action to the next.

**What changed for users**

| Feature | After |
|---|---|
| Palette | Four action items: *Export*, *Filter*, *Validation*, *Addition*. Clicking or dropping places the shape directly. |
| Connecting | Systems and actions connect by the rules of DATAFLOW.md §6.2. A disallowed target is marked while dragging, and releasing explains why. The second input of a Validation or Addition enters at the bottom and is dashed. |
| Setup | A new action is a dashed outline whose tooltip lists the missing connections. Once the last one is made, its dialog opens. Double-click or *Configure Action…* reopens it. |
| Export | Pick attributes from any incoming dataset. They become one new dataset in the target system, with lineage, shown in that system's shape. Duplicate names get the source dataset's name appended. |
| Filter | Uncheck datasets or attributes to drop. Copies of the rest (same names) go to the target system, with lineage. |
| Validation | Pair incoming datasets with the reference system's datasets, and attributes within each pair. Pairs are suggested by equal names, ignoring case. Compared datasets get an outline and a V-badge in the validation's colour. Selecting the Validation dims everything else. |
| Addition | Pick a dataset of the second system and relate attributes with a cardinality. The added dataset flows on to the next action. |
| Needs attention | When an input no longer has what an action uses, or something it used was deleted, the action gets an amber "!" and outline. The tooltip lists the problems. |
| Deleting | The Delete key asks first when the cascade removes relationships or changes actions. Deleting an action keeps the datasets it created. Copied action shapes get their own new action. |

**What changed in the code**

| File | Change |
|---|---|
| `js/diagramly/dataflow/DataFlowStreams.js` | **New.** Connection rules, streams, missing connections, configured check, action state. |
| `js/diagramly/dataflow/DataFlow.js` | Action and flow-edge styles and colours. |
| `js/diagramly/dataflow/DataFlowView.js` | Action shapes, labels, tooltips and states; flow-edge roles and styles (`syncEdge`); validation badges and outlines on datasets. Removed entities' shapes now go with their edges (`graph.removeCells`). |
| `js/diagramly/dataflow/DataFlowDialogs.js` | Export, Filter, Validation and Addition dialogs; stream tree; mapping rows. |
| `js/diagramly/dataflow/DataFlowUi.js` | `placeAction`, `configureAction`, `apply*`, `setDerivedAttributes`; hooks for copies, connections, validation errors, auto-open, delete confirmation and validation focus (ARCHITECTURE.md §20.3). |
| `js/diagramly/dataflow/DataFlowCatalog.js` | Removing an attribute also flags the Export or Filter that copied it (spec §6.3). The catalog test was updated. |
| [resources/dia.txt](../src/main/webapp/resources/dia.txt), [styles/grapheditor.css](../src/main/webapp/styles/grapheditor.css) | 45 `df*` strings; tree and mapping CSS. |
| [Devel.js](../src/main/webapp/js/diagramly/Devel.js), [build.xml](../etc/build/build.xml) | Load and compile `DataFlowStreams.js`. |
| `etc/test/dataflow/actions.test.js`, `harness.js` | **New:** 16 tests (64 in total). The harness now runs tests that return a Promise and closes all dialogs between tests. |
| `js/app.min.js`, `js/viewer*.min.js` | Rebuilt (the viewer bundles only for the strings). |
| [docs/DATAFLOW.md](DATAFLOW.md) | As-built notes in §5.4, §5.5, §6.3 and §8. |

**Impact on the codebase**

- **Built-in shapes only.** Action shapes and edges use built-in draw.io shapes and styles only, so the viewer and exports render them (checked with `viewer-static.min.js`).
- **Graph hooks.** `getEdgeValidationError`, `validationAlert` and `deleteCells` are wrapped per graph and only change behaviour for data flow cells. `validationAlert` now uses a draw.io dialog for every refused connection, which was `window.alert` before. Nothing else in draw.io returns validation errors.
- **Not built as designed** (recorded in DATAFLOW.md):
  - Action names are inside the shapes rather than below them.
  - The funnel is an inverted trapezoid.
  - A refused connection is explained on release rather than by a tooltip while dragging.

**Verification**

- `ant` builds with 0 errors.
- `node run.js` passes **64/64** against the rebuilt bundles and in dev mode (twice).
- Visual check in headless Firefox:
  - the full example chain: SAP → Filter → Staging → Validation (CRM) → Addition (Asset Register) → Export → Warehouse;
  - the Addition dialog;
  - validation focus;
  - the same file in `viewer-static.min.js`.

**Follow-ups**

None for this phase. Phase 4 (model view) is next.

### CHG-004 — Data flow diagrams, phase 2: systems and datasets

- **Date:** 2026-10-18
- **Status:** Done, follow-ups pending
- **ARCHITECTURE.md sections affected:** §2, §20

**Motivation**

Phase 2 of [DATAFLOW.md](DATAFLOW.md): systems and datasets can now be placed on the canvas, reused and edited. This is the first user-visible part of the feature.

**What changed for users**

| Feature | Before | After |
|---|---|---|
| Sidebar | — | New **Data Flow** palette above *General* with *System* and *Dataset*. It is always shown. |
| Placing a system | — | Drop or click *System*. The dialog offers an existing system of the page (optionally with its datasets) or a new one: name, owner, environment (suggested from the page) and notes. |
| Placing a dataset | — | Drop *Dataset* onto a system, click it with a system selected, or use *Add Dataset…* from the context menu. The dialog offers that system's datasets not yet in this shape, or a new one with the attribute editor (add, remove, reorder, Enter for a new row, paste a list of names). |
| Shapes | — | Systems: slate header with name, owner and environment chip; notes as tooltip. Datasets: collapsed by default with a +/− icon, table glyph, name and attribute count. Expanded datasets list one row per attribute. Systems grow and shrink with their content. |
| Editing | — | Double-click (or context menu) edits a system or dataset. Every shape of it updates. Removing attributes that are in use asks first. |
| Deleting | — | Deleting a shape removes that occurrence. Deleting the last one deletes the system or dataset. *Delete Everywhere…* removes it and all its shapes after confirmation. Everything is one undo step. |
| Drop rules | — | A system accepts only its own datasets. Datasets can't be dragged out of their system or into another system. |
| Viewer and exports | — | Show the shapes with no extra code (they are ordinary cells). |

**What changed in the code**

| File | Change |
|---|---|
| `js/diagramly/dataflow/DataFlow.js` | Colours, sizes and cell styles of systems, datasets and attribute rows. |
| `js/diagramly/dataflow/DataFlowView.js` | **New.** Creates the cells for entities. `sync` re-renders every shape from the catalog. `update` runs a catalog edit plus sync as one undoable edit. |
| `js/diagramly/dataflow/DataFlowDialogs.js` | **New.** System and Dataset dialogs and the attribute editor (dialog style guide conventions). |
| `js/diagramly/dataflow/DataFlowUi.js` | **New.** `DataFlowUi` (`ui.dataFlow`) and the hooks in ARCHITECTURE.md §20.3: `EditorUi.init`, `Sidebar.init`, `Sidebar.createDropHandler`, `Menus.createPopupMenu` (prototype wrappers), plus double-click, `REMOVE_CELLS`, `isValidDropTarget` and `shouldRemoveCellsFromParent` on each graph. |
| [resources/dia.txt](../src/main/webapp/resources/dia.txt) | 31 `df*` strings. |
| [styles/grapheditor.css](../src/main/webapp/styles/grapheditor.css) | `.geDataFlow*` classes for the attribute editor. |
| [js/diagramly/Devel.js](../src/main/webapp/js/diagramly/Devel.js), [etc/build/build.xml](../etc/build/build.xml) | Load and compile the three new files. |
| `etc/test/dataflow/ui.test.js` | **New.** 20 tests (48 in total). |
| `js/app.min.js`, `js/viewer.min.js`, `js/viewer-static.min.js` | Rebuilt. The viewer bundles only changed because they embed the `dia.txt` strings. |
| [docs/DATAFLOW.md](DATAFLOW.md) | §5.2, §5.3, §8 and §9 note where the build differs from the design. |

**Impact on the codebase**

- **Built-in shapes only.** Shapes use only built-in draw.io styles (swimlane plus stack layout, like the ER tables), so files open and render in any draw.io build. Other builds simply have no Data Flow editing.
- **Prototype wrappers.** `EditorUi.prototype.init`, `Sidebar.prototype.init`, `Sidebar.prototype.createDropHandler` and `Menus.prototype.createPopupMenu` are wrapped. Each wrapper calls the original first (or, for the drop handler, only for cells that are not data flow templates).
- **Not built as designed** (recorded in DATAFLOW.md):

  - There's no notes icon (tooltip only).
  - The environment chip sits beside the name.
  - There's no hover "+" (context menu instead).
- **Folding.** Datasets stay resizable, because draw.io only folds resizable containers. The stack layout keeps their size.
- **Known limitation:** cut and paste (see Follow-ups).

**Verification**

- `ant` builds with 0 errors and 0 warnings.
- `node run.js` passes **48/48** in dev mode and against the rebuilt bundles.
- Visual check in headless Firefox: editor shapes, fold icons, the Edit Dataset dialog, and the same file in `viewer-static.min.js`, which renders identically with no data flow code loaded.

### CHG-003 — Data flow diagrams, phase 1: the catalog

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §2, §20 (new)

**Motivation**

This is the first phase of the data flow diagrams ([DATAFLOW.md](DATAFLOW.md)). Systems, datasets, attributes, actions and relationships must be tracked independently of the shapes that draw them, so that they can be reused and related. This phase adds that store. Nothing is visible to users yet.

**What changed for users**

None. There is no UI yet (phase 2). Files without data flow content are unaffected.

**What changed in the code**

| File | Change |
|---|---|
| `js/diagramly/dataflow/DataFlow.js` | **New.** `DataFlow` namespace and constants. |
| `js/diagramly/dataflow/DataFlowCatalog.js` | **New.** `DataFlowCatalog`: entity CRUD, integrity cascades with removal reports, "needs attention" flags, load-time repair of untrusted JSON, and storage on the page root (`read`, `write`, `edit`). |
| [js/diagramly/Devel.js](../src/main/webapp/js/diagramly/Devel.js) | Loads the two files in dev mode. |
| [etc/build/build.xml](../etc/build/build.xml) | Compiles them into `app.min.js` (Step 9). |
| `etc/test/dataflow/` | **New.** Headless browser test runner (`run.js`, `harness.js`, puppeteer-core 23.11.1) and 28 tests (`catalog.test.js`, `storage.test.js`). |
| `js/app.min.js` | Rebuilt. |
| [docs/DATAFLOW.md](DATAFLOW.md) | Status updated. §4.2 now matches the implementation: an `attention` list per action, and Addition relationships are found through their `action` field instead of being listed in the configuration. |

**Impact on the codebase**

- **File format.** A page with data flow content has a `dataflow` attribute (JSON, versioned) on its root cell. The root then becomes a `UserObject` with an empty label, which is how draw.io already stores page data from *Edit Data*. Other draw.io builds open such files normally and keep the attribute.
- **Undo, sync and pages.** Catalog changes are ordinary cell value changes, so undo/redo, merge-on-save, page duplication and compression need no special handling. Two people editing the catalog at the same moment would conflict on that one attribute (accepted, as live sync is off in this deployment, DATAFLOW.md §4.1).
- **Security.** The catalog is untrusted input. IDs are validated, maps have no prototype, and `__proto__`/`constructor`/`prototype` are rejected (tested).
  - A first version listed the reserved IDs in an object literal. A quoted `'__proto__': true` in a literal sets the prototype instead of adding a key, so that check was silently ineffective. A test caught it, and the list is now an array.
- **Bundle size.** `app.min.js` grows by the compiled catalog code (about 35 KB of source before minification). The viewer bundles are unchanged.
- **Offline dev mode.** The generated service worker does not know the two new dev-mode files, so an offline `?dev=1` reload lacks them until it is regenerated (same follow-up as CHG-002).

**Verification**

- `node --check` passes for both files. `ant` builds with 0 Closure errors, and `app.min.js` contains the catalog.
- `node run.js` passes **28/28** in dev mode (`?dev=1`) and **28/28** against the rebuilt bundles, with no page errors.

**Follow-ups**

None for this phase. Phase 2 (systems and datasets on the canvas) is next.

Not changed, deliberately:

- The **diagram-language** feature (`Graph.diagramLanguage`, `label_xx`, the *Diagram Language* menu).
- `mxResources` and the `'languageChanged'` event listeners in grapheditor/diagramly (`EditorUi`, `Menus`, `Sidebar`, `Format`, `Pages`, `Minimal`, `Simple`, `App`, `Dialogs`). Nothing fires the event any more; the listeners are dormant and harmless.

### CHG-001 — Remove exports that depend on unavailable code

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §1, §3.2, §4.4, §7.4, §12.2, §13.6, §15, §16, §18

**Motivation**

Two export paths could never work in this fork:

1. **VSDX (Visio) export** calls `VsdxExport.js` and `mxVsdxCanvas2D.js`, which are not in the public repository. The menu item was already hidden at runtime (`vsdxExportEnabled()` was only true in Atlassian mode), but the action, the export function and the loader references remained.
2. **Server-side export** posted diagrams to `EXPORT_URL`, a separate Puppeteer export service that is not in this repository. In this deployment `PreConfig.js` set `EXPORT_URL = null`, so every server path was unreachable dead code. Server-side export covered PNG/JPEG when the canvas cannot be used (e.g. math is enabled), server-rendered PDF, the remote image export dialog, the image fallbacks for embedding and the embed protocol, and the `/export` reverse proxy in the Java backend.

The decision was to remove both entirely, rather than keep plumbing for a service we do not run.

**What changed for users**

| Feature | Before | After |
|---|---|---|
| File → Export as → VSDX | Hidden (code present) | Removed |
| File → Export as → PDF | Browser print dialog (server never configured) | Browser print dialog (unchanged). The desktop app still renders PDF files through its local pipeline |
| File → Export as → PNG/JPEG/WebP/Animation/SVG/HTML/XML/URL/JSON | Client-side | Unchanged |
| PNG/JPEG when the canvas cannot be used (math enabled) | Menu items hidden (no server) | Unchanged: still hidden |
| File → Export as → Advanced… (generic export dialog) | PNG/JPEG/SVG client-side; other formats tried the server | PNG/JPEG/SVG client-side; anything else shows "Not available" |
| Embed protocol `export` with `png`/`xmlpng` when the canvas cannot be used | Replied without data (no server) | Unchanged: replies without data |
| Server endpoints `/export`, `/service/*` | Proxied to the `EXPORT_URL` env var (unset) | Removed (404) |

In practice there is **no visible change for users of this deployment**, because none of the removed paths were reachable. The change removes about 790 lines of dead or broken code.

**What changed in the code**

| File | Change |
|---|---|
| [js/diagramly/Menus.js](../src/main/webapp/js/diagramly/Menus.js) | Removed the `exportVsdx` action and its menu entry. Removed the remote-export branch of `exportImage` (which used `showRemoteExportDialog`). `exportPdf` now always uses the print dialog in the browser and only passes an export callback in Electron. The `exportAs` menu now lists PDF unconditionally and no longer checks `isRemoteExportEnabled`/`isPrintPdfExport`/`vsdxExportEnabled`. |
| [js/diagramly/EditorUi.js](../src/main/webapp/js/diagramly/EditorUi.js) | Removed `printPdfExport`, `isRemoteExportEnabled()`, `isPrintPdfExport()`, the browser `createDownloadRequest()` (which posted to `EXPORT_URL`), `showRemoteExportDialog()`, `exportVisio()` and `vsdxExportEnabled()`. `downloadFile()` lost its embed-protocol server branch and now shows "Not available" for rendered formats unless `createDownloadRequest` exists (it is defined only by `ElectronApp.js`). Not changed, deliberately:

- **`export3.html`, `js/export.js`, `js/export-init.js`, `export-fonts.css`** are the headless rendering page. Nothing in the web app uses it any more, but drawio-desktop's local export pipeline (the `createDownloadRequest` override in `ElectronApp.js`) and command-line export render through it, so it is kept for desktop compatibility.
- **Online-service exports that do not need missing code** (Export as URL, Publish link, Embed → HTML/IFrame/Notion, which use `viewer.diagrams.net`) are kept.

**Impact on the codebase**

- **Prebuilt bundles are stale.** The committed `js/app.min.js`, `js/viewer.min.js`, `js/viewer-static.min.js` and `js/integrate.min.js` still contain the old code. Dev mode (`?dev=1`) runs the new sources. Normal mode runs the old bundles until they are rebuilt. A JDK and Ant are not installed on the development machine, so they could not be rebuilt as part of this change.
- **Temporary guard.** The stale bundles default `EXPORT_URL` to `https://convert.diagrams.net/node/export` when it is undefined, which would have re-enabled server export to an external service in normal mode. `js/PreConfig.js` therefore still sets `window.EXPORT_URL = null`, marked TEMPORARY, until the bundles are rebuilt.
- **API removals.** Plugins or integrations that called `ui.isRemoteExportEnabled()`, `ui.isPrintPdfExport()`, `ui.showRemoteExportDialog()`, `ui.exportVisio()` or `ui.vsdxExportEnabled()`, or that relied on the `EXPORT_URL` global, will now fail. None of the plugins in `plugins/` use them.
- **Desktop (Electron).** Unaffected: PDF export and `getEmbeddedPdf` still use the Electron `createDownloadRequest` override plus `downloadRequestBuilder`.
- **Server.** The WAR no longer serves `/export` or `/service/*`, and the `EXPORT_URL` environment variable is no longer read. All other servlets are unchanged.
- **Security.** This removes a path that could transmit diagram content to an external server.
