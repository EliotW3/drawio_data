# drawio_data — Fork Change Log

This file records every change made to this fork of draw.io and its effect on the application and codebase. It is the companion to [ARCHITECTURE.md](ARCHITECTURE.md): the architecture guide describes how the code works *now*, and this log explains *what was changed from upstream and why*.

The upstream release log is [ChangeLog](../ChangeLog) in the repository root. Do not add fork changes there.

## How to record a change

- Add a new entry at the **top** of [Change entries](#change-entries) with the next ID (`CHG-012`, `CHG-013`, …), and add a row to the [Change index](#change-index).
- Fill in every heading of the template below. Write "None" rather than deleting a heading.
- Reference [ARCHITECTURE.md](ARCHITECTURE.md) sections by number (e.g. "§12.2") and update those sections in the same change, so that the architecture guide always describes the current code.
- List anything left unfinished under **Follow-ups**, and keep [Open follow-ups](#open-follow-ups) in sync until the item is resolved.

```markdown
### CHG-NNN — <short title>

- **Date:** YYYY-MM-DD
- **Status:** Done | Done, follow-ups pending | Reverted
- **ARCHITECTURE.md sections affected:** §x.y, …

**Motivation** — why the change was made.

**What changed for users** — visible behaviour before → after.

**What changed in the code** — files, functions, removed/added APIs.

**Impact on the codebase** — dependencies, load order, bundles, server, configuration, compatibility (desktop, embed, viewer).

**Verification** — how it was tested and the result.

**Follow-ups** — remaining work, or "None".
```

### CHG-011 — Desktop build workflow: tests on Linux, Node 24 actions

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §21.1

**Motivation**

The first run of *Desktop app (Windows)* failed:
- **The real failure:** its "Test the main process" step failed on `windows-latest`. The draw.io desktop tests assume POSIX paths, and upstream only runs them on macOS and Linux; on Linux all of them pass. The install step passed, and the build was skipped.
- **A warning, not the cause:** GitHub also warned that `actions/checkout@v4` and `actions/setup-node@v4` target the deprecated Node 20.

**What changed for users**

None. The installer is the same.

**What changed in the code**

| File | Change |
|---|---|
| [.github/workflows/desktop-windows.yml](../.github/workflows/desktop-windows.yml) | Split into a `test` job (`ubuntu-latest`, `npm test`) and a `build` job (`windows-latest`, `npm run dist-win`, upload, release) that runs only after `test` passes. Actions moved to their Node 24 versions: `actions/checkout@v6`, `actions/setup-node@v6`, `actions/upload-artifact@v6`, `softprops/action-gh-release@v3` (checked to declare `node24`). |

**Impact on the codebase**

The Windows build no longer runs the main-process tests on Windows. That matches upstream, and the tests still gate the build.

**Verification**

- The failing step was identified from the run's job data (run 39158031468, job "build": step 5 "Test the main process" failed, steps 6–8 skipped).
- `npm test` passes locally on Linux (273 passed, 1 skipped).
- The workflow file parses, and every action version was checked to exist and run on Node 24.
- The new workflow has not run yet; that needs a push.

**Follow-ups**

None.

### CHG-010 — Installer option for .drawio files; usage instructions

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §21.1

**Motivation**

People who already have draw.io should be able to install drawio-data without it taking over draw.io. The app was already separate (own folder, app ID and settings), but the installer made itself the default app for `.drawio` files without asking. The README also needed step-by-step instructions for both ways of running the fork.

**What changed for users**

| Feature | Before | After |
|---|---|---|
| `.drawio` files | The installer always made drawio-data their default app | A *Diagram files* page asks. The box starts unchecked when another app (such as draw.io) already opens them. drawio-data is always offered under *Open with*. |
| Uninstall | Removed electron-builder's association | Removes only what drawio-data added, and gives `.drawio` back only if drawio-data was its default |
| README | Short "Use it" section | Step-by-step guides: *Option 1: run it in your browser (localhost)* for Windows, macOS and Linux, with Git or ZIP, Python or Node; and *Option 2: install it as a Windows application* (SmartScreen, the file option, using it next to draw.io, update, uninstall); plus *Developing* |

**What changed in the code**

| File | Change |
|---|---|
| `desktop/build/installer.nsh` | **New.** NSIS additions through electron-builder's hooks: `customInit` (default of the option), `customPageAfterChangeDir` (the page), `customInstall` (ProgID, *Open with*, optional default) and `customUnInstall`. |
| `desktop/electron-builder-win.json` | `nsis.include` added; `fileAssociations` removed (the script handles them). |
| [README.md](../README.md), [desktop/README.md](../desktop/README.md) | Usage instructions as above. |

**Impact on the codebase**

- **Registry.** The installer writes only under the user's `Software\Classes` (per-user install): the `drawio-data.drawio` ProgID, its *Open with* entry, and the `.drawio` default only when chosen.
- **Silent installs** (`/S`) use the default: drawio-data opens `.drawio` files only if no other app does.

**Verification**

- `npm run dist-win` builds the installer, so the script compiles in the real installer.
- The same `installer.nsh` was compiled into a test installer and uninstaller with electron-builder's NSIS and run under Wine. It passed five cases:
  - no app for `.drawio`: drawio-data becomes the default, the *Open with* entry and ProgID are written, and the option is checked;
  - uninstall: everything is removed;
  - `.drawio` owned by `draw.io.drawio`: the default is unchanged, the *Open with* entry is added, and the option is unchecked;
  - uninstall: draw.io stays the default;
  - reinstall over drawio-data: it stays the default.
- **Not verified:** the full installer doesn't run under Wine. A plain electron-builder installer without these additions stops there too (exit code 2), so it is a Wine limit. Seeing the page and installing on Windows is still the CHG-009 follow-up.

**Follow-ups**

None beyond CHG-009's (try the installer on Windows).

### CHG-009 — Windows desktop app

- **Date:** 2026-10-18
- **Status:** Done, follow-ups pending
- **ARCHITECTURE.md sections affected:** §2, §21 (new)

**Motivation**

Users should be able to download the app and run it as an application, on Windows, without Git, a web server or a browser tab.

**What changed for users**

- **Install.** There is a Windows installer (`drawio-data-<version>-windows-installer.exe`). It installs per user, needs no administrator rights, adds Start menu and desktop shortcuts, and opens `.drawio` files.
- **App.** It runs the editor of this repository, including the data flow diagrams, in its own window with native open and save dialogs, and works offline.
- **Alongside official draw.io.** It installs next to an official draw.io desktop and keeps its own settings.
- **Updates.** It doesn't update itself.
- **SmartScreen.** The installer is unsigned, so SmartScreen may warn on first run.
- **README.** The root README now starts with how to use this fork (installer, browser, development).

**What changed in the code**

| File | Change |
|---|---|
| `desktop/` | **New**, GPL-3.0. Taken from draw.io desktop v32.5.5: main process, tests, icons, fuses hook. Adapted: `package.json` (name `drawio-data`, scripts `start`, `dist-win`, `test`; no signing, notarising or macOS dependencies), `electron-builder-win.json` (own app ID, per-user NSIS, no publish), `scripts/prepare.cjs` (replaces `sync.cjs`), `README.md`. |
| `desktop/src/main/electron.js` | Three changes: adds the ` draw.io/<version>` user-agent token so the web app runs in desktop mode; drops the `export` URL parameter (export service removed in CHG-001); *Report issue* opens this repository. |
| `desktop/src/main/disableUpdate.js` | Always `true`: updates would install upstream draw.io over the fork. The upstream update-channel test was removed. |
| [.github/workflows/desktop-windows.yml](../.github/workflows/desktop-windows.yml) | **New.** Builds and tests on Windows. Uploads the installer as an artifact, and for `desktop-v*` tags publishes a GitHub Release. |
| [.gitignore](../.gitignore) | `!desktop/build/`, because the existing `build` rule (Ant output) also matched the desktop icons folder. |
| [README.md](../README.md) | New fork section at the top: what this is, the installer, running in a browser from a clone, and development. |

**Impact on the codebase**

- **Licence.** `desktop/` is GPL-3.0; the rest of the repository stays Apache-2.0. The built desktop app is a GPL-3.0 work, so anyone given the installer must be able to get its source, which they can from this repository.
- **No changes to the web app.** The desktop app copies `src/main/webapp` at build time and uses `js/app.min.js`, so the bundles must be rebuilt before a desktop build.
- **Repository size.** `desktop/node_modules`, `desktop/dist` and `desktop/drawio` are ignored. The committed folder is under 1 MB.

**Verification**

- `npm test` in `desktop/`: 273 passed, 1 skipped (upstream tests minus update-channel).
- **Electron launch on Linux** (`npm start`), driven over the DevTools protocol:
  - the web app runs in desktop mode (`mxIsElectron` true, `window.electron` present, updates off, English);
  - the Data Flow palette is present;
  - placing a system with a dataset and switching to the model view works.
- `npm run dist-win` on Linux with Wine built `drawio-data-32.5.5-windows-installer.exe` (156 MB). Its `app.asar` contains the current `app.min.js` with the data flow code and `disableUpdate` → `true`, and leaves out sources, tests and `WEB-INF`.
- **Not verified:** the installer was not run on Windows, because no Windows machine was available (see Follow-ups).

**Follow-ups**

### CHG-008 — Data flow cardinalities use M for "many"

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §20.2, §20.4

**Motivation**

The cardinalities mixed N and M for "many" (`1:N`, `N:1`, `N:M`). They now use M throughout: `1:1`, `1:M`, `M:1`, `M:M`.

**What changed for users**

The cardinality picker, relationship labels and the Addition dialog show `1:M (one to many)`, `M:1 (many to one)` and `M:M (many to many)`. Files saved with the old values open with the new ones. The markers are unchanged.

**What changed in the code**

| File | Change |
|---|---|
| `DataFlow.js` | `CARDINALITIES` is `['1:1', '1:M', 'M:1', 'M:M']`. New `LEGACY_CARDINALITIES` and `normalizeCardinality`. |
| `DataFlowCatalog.js` | Load, `addRelationship` and `setCardinality` convert the old forms. The default for an invalid value is `1:M`. |
| `DataFlowDialogs.js`, [resources/dia.txt](../src/main/webapp/resources/dia.txt) | Picker keys and default; strings `dfCard1M`, `dfCardM1`, `dfCardMM` replace `dfCard1N`, `dfCardN1`, `dfCardNM`. |
| `etc/test/dataflow/*.test.js` | Values updated. One new test covers loading old files (91 in total). |
| `js/app.min.js`, `js/viewer*.min.js` | Rebuilt. |

**Impact on the codebase**

- **Format.** Stored relationships are written with M from now on. Older builds of this fork would read `1:M` as invalid and reset it to `1:N`, so files edited here should not go back to a build from before this change.
- **Older CHANGES entries** keep the N notation they were written with.

**Verification**

`ant` builds with 0 errors. `node run.js` passes **91/91** in dev mode and against the rebuilt bundles.

**Follow-ups**

None.

### CHG-007 — Data flow diagrams, phase 5: copy and paste, performance

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §2, §20 (finished: §20.5–§20.8)

**Motivation**

Phase 5 of [DATAFLOW.md](DATAFLOW.md): make the feature robust. Cut and paste lost data (CHG-004 follow-up), pasting into another page or file had no catalog to draw from, and performance at a realistic size was unmeasured.

**What changed for users**

| Feature | Before | After |
|---|---|---|
| Copy and paste on the same page | Worked | Unchanged (another shape of the same system or dataset) |
| Cut and paste | Lost the systems and datasets | Restores them with the same IDs and attributes |
| Paste into another page or file, library (scratchpad) drops | Shapes without data, removed on the next edit | Systems, datasets, attributes and actions come along. Actions whose output didn't come along are unconfigured. |
| A dataset pasted on its own | Could land outside a system | Goes into a shape of its system that doesn't show it yet, otherwise it is dropped |
| Model-view cells pasted into the flow | Could leave stray tables | Dropped |
| First switch to the model view | — | About 10% faster |

**What changed in the code**

| File | Change |
|---|---|
| `DataFlowCatalog.js` | `extract` (fragment of given entities) and `importFragment` (adds missing entities with their IDs, validated like a loaded file). |
| `DataFlowUi.js` | Per-graph `encodeCells` wrapper and `addFragments` (adds `dfData`). `cellsAdded` rewritten: import, strip, placement rules, action copies, cleanup of imported entities without shapes. |
| `DataFlowModel.js` | `sync(…, noPlacement)`; the first switch skips per-table placement. |
| `etc/test/dataflow/clipboard.test.js`, `perf.test.js` | **New:** 10 tests (90 in total). `harness.js`/`run.js` print notes (timings). |
| `js/app.min.js` | Rebuilt. |
| [docs/ARCHITECTURE.md](ARCHITECTURE.md) | §20 finished: copy and paste (§20.5), performance (§20.6), extending the feature (§20.7). The section is no longer marked in progress. |
| [docs/DATAFLOW.md](DATAFLOW.md) | Status: implemented; phase 5 as-built note. |

**Impact on the codebase**

- **Copied XML is larger.** It now carries `dfData` on data flow cells: the entity data, which is diagram content. Pasted cells don't keep it.
- **Clipboard data is untrusted input.** It goes through the same validation as files: invalid IDs, `__proto__` and dangling references are dropped, and labels are re-rendered from the validated catalog and escaped (tested).
- **`encodeCells` is wrapped per graph** and only adds attributes to the encoded copy, never to the page.

**Verification**

- `ant` builds with 0 errors.
- `node run.js` passes **90/90** in dev mode and against the rebuilt bundles.
- Performance at 50 systems / 500 datasets / 25 exports:
  - an edit takes about 80 ms, and configuring an Export about 135 ms;
  - an edit in the model view takes about 125 ms;
  - the first model view takes about 2.2 s, and later switches 0.6–1.6 s.

**Follow-ups**

None for the feature. The style points A–D from the mock-up and the optional View-menu entry (CHG-006) remain open.

### CHG-005 — Data flow diagrams, phase 3: actions

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §20

**Motivation**

Phase 3 of [DATAFLOW.md](DATAFLOW.md): the four actions (Export, Filter, Validation, Addition), the connection rules, and the streams that carry datasets from one action to the next.

**What changed for users**

| Feature | After |
|---|---|
| Palette | Four action items: *Export*, *Filter*, *Validation*, *Addition*. Clicking or dropping places the shape directly. |
| Connecting | Systems and actions connect by the rules of DATAFLOW.md §6.2. A disallowed target is marked while dragging, and releasing explains why. The second input of a Validation or Addition enters at the bottom and is dashed. |
| Setup | A new action is a dashed outline whose tooltip lists the missing connections. Once the last one is made, its dialog opens. Double-click or *Configure Action…* reopens it. |
| Export | Pick attributes from any incoming dataset. They become one new dataset in the target system, with lineage, shown in that system's shape. Duplicate names get the source dataset's name appended. |
| Filter | Uncheck datasets or attributes to drop. Copies of the rest (same names) go to the target system, with lineage. |
| Validation | Pair incoming datasets with the reference system's datasets, and attributes within each pair. Pairs are suggested by equal names, ignoring case. Compared datasets get an outline and a V-badge in the validation's colour. Selecting the Validation dims everything else. |
| Addition | Pick a dataset of the second system and relate attributes with a cardinality. The added dataset flows on to the next action. |
| Needs attention | When an input no longer has what an action uses, or something it used was deleted, the action gets an amber "!" and outline. The tooltip lists the problems. |
| Deleting | The Delete key asks first when the cascade removes relationships or changes actions. Deleting an action keeps the datasets it created. Copied action shapes get their own new action. |

**What changed in the code**

| File | Change |
|---|---|
| `js/diagramly/dataflow/DataFlowStreams.js` | **New.** Connection rules, streams, missing connections, configured check, action state. |
| `js/diagramly/dataflow/DataFlow.js` | Action and flow-edge styles and colours. |
| `js/diagramly/dataflow/DataFlowView.js` | Action shapes, labels, tooltips and states; flow-edge roles and styles (`syncEdge`); validation badges and outlines on datasets. Removed entities' shapes now go with their edges (`graph.removeCells`). |
| `js/diagramly/dataflow/DataFlowDialogs.js` | Export, Filter, Validation and Addition dialogs; stream tree; mapping rows. |
| `js/diagramly/dataflow/DataFlowUi.js` | `placeAction`, `configureAction`, `apply*`, `setDerivedAttributes`; hooks for copies, connections, validation errors, auto-open, delete confirmation and validation focus (ARCHITECTURE.md §20.3). |
| `js/diagramly/dataflow/DataFlowCatalog.js` | Removing an attribute also flags the Export or Filter that copied it (spec §6.3). The catalog test was updated. |
| [resources/dia.txt](../src/main/webapp/resources/dia.txt), [styles/grapheditor.css](../src/main/webapp/styles/grapheditor.css) | 45 `df*` strings; tree and mapping CSS. |
| [Devel.js](../src/main/webapp/js/diagramly/Devel.js), [build.xml](../etc/build/build.xml) | Load and compile `DataFlowStreams.js`. |
| `etc/test/dataflow/actions.test.js`, `harness.js` | **New:** 16 tests (64 in total). The harness now runs tests that return a Promise and closes all dialogs between tests. |
| `js/app.min.js`, `js/viewer*.min.js` | Rebuilt (the viewer bundles only for the strings). |
| [docs/DATAFLOW.md](DATAFLOW.md) | As-built notes in §5.4, §5.5, §6.3 and §8. |

**Impact on the codebase**

- **Built-in shapes only.** Action shapes and edges use built-in draw.io shapes and styles only, so the viewer and exports render them (checked with `viewer-static.min.js`).
- **Graph hooks.** `getEdgeValidationError`, `validationAlert` and `deleteCells` are wrapped per graph and only change behaviour for data flow cells. `validationAlert` now uses a draw.io dialog for every refused connection, which was `window.alert` before. Nothing else in draw.io returns validation errors.
- **Not built as designed** (recorded in DATAFLOW.md):
  - Action names are inside the shapes rather than below them.
  - The funnel is an inverted trapezoid.
  - A refused connection is explained on release rather than by a tooltip while dragging.

**Verification**

- `ant` builds with 0 errors.
- `node run.js` passes **64/64** against the rebuilt bundles and in dev mode (twice).
- Visual check in headless Firefox:
  - the full example chain: SAP → Filter → Staging → Validation (CRM) → Addition (Asset Register) → Export → Warehouse;
  - the Addition dialog;
  - validation focus;
  - the same file in `viewer-static.min.js`.

**Follow-ups**

None for this phase. Phase 4 (model view) is next.

**Impact on the codebase**

- **File format.** A page with data flow content has a `dataflow` attribute (JSON, versioned) on its root cell. The root then becomes a `UserObject` with an empty label, which is how draw.io already stores page data from *Edit Data*. Other draw.io builds open such files normally and keep the attribute.
- **Undo, sync and pages.** Catalog changes are ordinary cell value changes, so undo/redo, merge-on-save, page duplication and compression need no special handling. Two people editing the catalog at the same moment would conflict on that one attribute (accepted, as live sync is off in this deployment, DATAFLOW.md §4.1).
- **Security.** The catalog is untrusted input. IDs are validated, maps have no prototype, and `__proto__`/`constructor`/`prototype` are rejected (tested).
  - A first version listed the reserved IDs in an object literal. A quoted `'__proto__': true` in a literal sets the prototype instead of adding a key, so that check was silently ineffective. A test caught it, and the list is now an array.
- **Bundle size.** `app.min.js` grows by the compiled catalog code (about 35 KB of source before minification). The viewer bundles are unchanged.
- **Offline dev mode.** The generated service worker does not know the two new dev-mode files, so an offline `?dev=1` reload lacks them until it is regenerated (same follow-up as CHG-002).

**Verification**

- `node --check` passes for both files. `ant` builds with 0 Closure errors, and `app.min.js` contains the catalog.
- `node run.js` passes **28/28** in dev mode (`?dev=1`) and **28/28** against the rebuilt bundles, with no page errors.

None for this phase. Phase 2 (systems and datasets on the canvas) is next.

### CHG-001 — Remove exports that depend on unavailable code

- **Date:** 2026-10-18
- **Status:** Done
- **ARCHITECTURE.md sections affected:** §1, §3.2, §4.4, §7.4, §12.2, §13.6, §15, §16, §18

**Motivation**

Two export paths could never work in this fork:

1. **VSDX (Visio) export** calls `VsdxExport.js` and `mxVsdxCanvas2D.js`, which are not in the public repository. The menu item was already hidden at runtime (`vsdxExportEnabled()` was only true in Atlassian mode), but the action, the export function and the loader references remained.
2. **Server-side export** posted diagrams to `EXPORT_URL`, a separate Puppeteer export service that is not in this repository. In this deployment `PreConfig.js` set `EXPORT_URL = null`, so every server path was unreachable dead code. Server-side export covered PNG/JPEG when the canvas cannot be used (e.g. math is enabled), server-rendered PDF, the remote image export dialog, the image fallbacks for embedding and the embed protocol, and the `/export` reverse proxy in the Java backend.

The decision was to remove both entirely, rather than keep plumbing for a service we do not run.

**What changed for users**

| Feature | Before | After |
|---|---|---|
| File → Export as → VSDX | Hidden (code present) | Removed |
| File → Export as → PDF | Browser print dialog (server never configured) | Browser print dialog (unchanged). The desktop app still renders PDF files through its local pipeline |
| File → Export as → PNG/JPEG/WebP/Animation/SVG/HTML/XML/URL/JSON | Client-side | Unchanged |
| PNG/JPEG when the canvas cannot be used (math enabled) | Menu items hidden (no server) | Unchanged: still hidden |
| File → Export as → Advanced… (generic export dialog) | PNG/JPEG/SVG client-side; other formats tried the server | PNG/JPEG/SVG client-side; anything else shows "Not available" |
| Embed protocol `export` with `png`/`xmlpng` when the canvas cannot be used | Replied without data (no server) | Unchanged: replies without data |
| Server endpoints `/export`, `/service/*` | Proxied to the `EXPORT_URL` env var (unset) | Removed (404) |

In practice there is **no visible change for users of this deployment**, because none of the removed paths were reachable. The change removes about 790 lines of dead or broken code.
